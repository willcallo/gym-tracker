# Gym Tracker plan: user accounts, then an iOS app

Written 2026-11-16 from a review of the codebase at commit `0303279`. No code has been changed yet.

## Context

The app sits behind one shared password (`APP_PASSWORD`), and every table is global, so you and your friends currently read and write the same sessions, exercises, settings and AI summary. The goal is separate accounts where each person only sees and edits their own data, using an auth setup that a future mobile app can reuse, at free-tier cost.

Decisions you made: existing data can be wiped, sign-up is by invite code, login is email + password, exercises are per-user with a starter set. After accounts, an iOS app with lock-screen Live Activities, paid Apple developer account, aiming for the App Store (section 7).

## 1. How the app is structured now

- **Next.js 16.2.9 App Router, React 19, Tailwind 4, `pg` against Neon, Anthropic SDK.** Six runtime dependencies, no ORM, no test framework.
- **Reads** happen in server components that call `lib/db.ts` directly: `app/page.tsx`, `app/log/page.tsx`, `app/history/**`, `app/exercises/**`, `app/settings/page.tsx`.
- **Writes** all go through JSON route handlers under `app/api/**`. There are **no server actions** anywhere. This is good for mobile: the write API already exists.
- **`lib/db.ts`** (482 lines) is the only data access layer: about 20 exported functions, all hand-written parameterised SQL. None take a user.
- **Auth** is `lib/auth.ts` + `proxy.ts` (Next 16's replacement for middleware) + `app/api/login`, `app/api/logout`. The proxy is the only gate: it checks an HMAC-signed cookie that carries a timestamp and nothing else. Route handlers and pages do no checks of their own.
- **Schema** is `lib/schema.sql`: `exercises`, `sessions`, `sets`, plus single-row `settings` and `training_summary` tables. It is applied on every Vercel build by `scripts/db-init.mjs`, which refuses destructive SQL.
- **AI**: `lib/ai.ts` builds prompts, called from `POST /api/sessions/[id]/coaching` and `POST /api/training-summary`.
- **Client state**: unsaved session drafts and the rest timer live in `localStorage` (`lib/draftStore.ts`, `lib/hooks/useRestTimer.ts`).

## 2. Auth approach

**Recommended: Better Auth, storing users and sessions in your existing Neon database.**

- Email + password built in, sessions are opaque tokens in a `session` table (revocable, per device), cookies for web.
- Works for the iOS app in section 7 with no extra code (the app's web view keeps the session cookie), and has an Expo plugin if you ever move to a fully native app.
- Free: it is a library, not a service. No per-user limits, nothing else to sign up for.
- Users live in the same database as the data, so `user_id` columns get real foreign keys and `ON DELETE CASCADE`, and Neon preview branches work with no extra setup.
- Adding Google/Apple login, password-reset emails or passkeys later is configuration, not a rewrite.

**Main alternative: Clerk (hosted).** Faster to set up, ready-made UI, good Expo SDK, generous free tier. I would not pick it here because users live outside your database (no foreign keys, account deletion needs a webhook), every Vercel preview URL needs configuring on their side, and the mobile app becomes tied to their SDK and pricing.

Not recommended: extending the hand-rolled auth in `lib/auth.ts`. It is feasible for three users, but password reset, rate limiting and mobile token handling are exactly what you would end up rebuilding.

**To verify at step 1, not assumed:** that the current Better Auth release documents Next 16 `proxy.ts`, and the exact names of its invite/sign-up hook and rate-limit storage option. `AGENTS.md` also requires reading `node_modules/next/dist/docs/` before writing code; that folder was not present in this checkout, so run `npm install` first.

**Shape of the integration**

- `lib/auth.ts` is replaced: Better Auth instance using the existing `pg` pool, plus one helper `requireUser()` that returns `{ id, email }` or throws/redirects. Every page and route calls it. Keep `safeNext()`.
- `app/api/auth/[...all]/route.ts` replaces `app/api/login` and `app/api/logout`.
- `proxy.ts` keeps only a cheap "is there a session cookie" redirect to `/login`. It is no longer the security boundary.
- Sign-up requires `INVITE_CODE` (env var), checked server-side in a before-sign-up hook, compared in constant time.
- Env vars: remove `APP_PASSWORD`, `AUTH_DISABLED`, `SESSION_SECRET`. Add `BETTER_AUTH_SECRET`, `INVITE_CODE`, and a base URL derived from `VERCEL_URL` on previews. Auth is always on, including local dev.

## 3. Schema changes and migration

Because the data can be wiped, `lib/schema.sql` is rewritten to its final shape rather than migrated column by column.

| Table | Change |
| --- | --- |
| `"user"`, `session`, `account`, `verification` | New, generated by the Better Auth CLI and pasted into `schema.sql` as `CREATE TABLE IF NOT EXISTS`. `user.id` is `TEXT`. |
| `exercises` | Add `user_id TEXT NOT NULL REFERENCES "user"(id) ON DELETE CASCADE`. Name uniqueness becomes `(user_id, lower(name))`. Add `UNIQUE (id, user_id)`. |
| `sessions` | Add `user_id` (same definition). Index becomes `(user_id, date DESC, id DESC)`. `client_key` uniqueness becomes `(user_id, client_key)`. Add `UNIQUE (id, user_id)`. |
| `sets` | Add `user_id`. Replace the two single-column foreign keys with composite ones: `(session_id, user_id) → sessions(id, user_id)` and `(exercise_id, user_id) → exercises(id, user_id)`. The database itself then rejects a set that links one user's session to another user's exercise. |
| `settings` | Primary key becomes `user_id` instead of the single-row boolean. Drop the seed `INSERT`. |
| `training_summary` | Primary key becomes `user_id`. |
| `ai_usage` | New: `(user_id, day DATE, count INT, PRIMARY KEY (user_id, day))` for a daily AI cap. |

Row-level security is deliberately not used: one pooled role and hand-written SQL make it more machinery than it is worth here. The composite keys cover the cross-user integrity case.

**Migration (wipe)**

1. `scripts/db-reset.mjs`: add the new tables to `TABLES`.
2. `scripts/db-init.mjs`: add a preflight that fails with a clear message if `sessions` exists without `user_id`. Without this, the first deploy would fail on an obscure index error, because `CREATE TABLE IF NOT EXISTS` leaves old-shaped tables alone.
3. Preview: run `ALLOW_RESET=yes npm run db:reset` once against the preview branch's database (each preview starts as a copy of production).
4. Production cutover: run the same reset against production, then merge. The live site errors for the minute or two between reset and deploy; tell your friends beforehand.
5. `scripts/seed.mjs` takes a user email and seeds that account only.

## 4. Where user checks are needed

There are no server actions. Every item below calls `requireUser()` and passes `user.id` into `lib/db.ts`. Another user's id returns 404, not 403, which falls out of adding `AND user_id = $n` to each query.

**API routes**

| `app/api/exercises/route.ts` | POST | `createExercise` |

| `app/api/login/route.ts`, `app/api/logout/route.ts` | | Deleted, replaced by `app/api/auth/[...all]/route.ts` |

| File | DB functions to scope |

**Queries in `lib/db.ts` that are easy to miss** (they have no id parameter today, so a quick pass would leave them global)

- `getCoachingContext`: the `prior` CTE reads every session in the database. Unscoped, a friend's lifts would feed your coaching note.
- `getSummaryContext`: all three subqueries and the date-range query are global.
- `getExerciseOverview`: `SELECT count(*) FROM sessions` and the `training_summary` join.
- `LAST_SETS_JOINS` and the PR subquery over `sets`.
- `createSession`: the `client_key` fallback `SELECT id FROM sessions WHERE client_key = $1` would return another user's session id on a key collision.
- `createSession` / `updateSession`: `exercise_id` values from the request body are never checked for ownership. The composite foreign key fixes this, and the existing `23503` handler already returns "One of the exercises no longer exists".

Changing each function's signature to take `userId` first makes TypeScript list every caller, so none can be missed silently.

## 5. Security problems and bad code, ranked

1. **The proxy is the only auth check.** No route handler or page verifies anything itself, so a matcher mistake or a framework proxy bypass exposes everything. Fixed by `requireUser()` in every handler and page.
2. **Cross-user leaks through aggregate queries** (the list in section 4). Not a bug today, but the most likely way this change goes wrong.
3. **No limit on AI spend.** Any signed-in user can call the two AI routes in a loop on your Anthropic key. With accounts and an invite code that can leak, add a per-user daily cap (`ai_usage`, about 20 calls a day).
4. **Login is not rate limited.** The one-second sleep in `app/api/login/route.ts` does not stop parallel guesses, and the README relies on a Vercel rule that may not exist. Use Better Auth's rate limiter with database storage (in-memory storage does nothing on serverless).
5. **The current session cookie is weak.** Valid for a year, cannot be revoked, logout only clears it in the browser, and if `SESSION_SECRET` is unset a captured cookie allows offline guessing of the shared password. Removed by the auth replacement.
6. **Drafts are stored under a global `localStorage` key** (`gym:draft:new`). On a shared phone or browser, the next person to sign in is offered the previous person's unsaved session. Namespace the keys by user id and clear them on sign-out.
7. **Preview deployments copy production data**, which will now include friends' sessions and password hashes. Acceptable, but keep previews behind Vercel's deployment protection and use a different `BETTER_AUTH_SECRET` there.

Checked and fine: all SQL is parameterised, input validation in `lib/validate.ts` is thorough, AI output is rendered as text (no `dangerouslySetInnerHTML`), `safeNext()` handles open redirects, security headers are set.

## 6. Implementation order

Each step is one branch-sized change you can run and test before the next.

1. **Add Better Auth beside nothing else.** `npm install`, read the Next 16 docs for proxy and route handlers, add the auth tables to `schema.sql`, the auth instance, `app/api/auth/[...all]/route.ts`, sign-up (with invite code) and sign-in forms replacing `app/login/LoginForm.tsx`. Delete the old login/logout routes and `APP_PASSWORD` logic. *Test: sign up with and without the right code, sign in, sign out, see rows in `user` and `session`. Data is still shared at this point.*
2. **`requireUser()` everywhere.** Add the helper and call it in all 7 route files and 8 pages; slim `proxy.ts` to a redirect. *Test: `curl` each API route with no cookie and get 401.*
3. **Schema rewrite + exercises and settings.** New `schema.sql`, `db-reset` and `db-init` changes, local `db:reset`. Convert `createExercise`, `updateExercise`, `deleteExercise`, `getExerciseDetail`, `getSettings`, `saveSettings` and their callers. *Test: two accounts, each can create "Bench Press", neither sees the other's.*
4. **Sessions and sets.** Convert `getSessionsPage`, `getSession`, `createSession`, `updateSession`, `deleteSession`, `getExercisesForLog`, `getExerciseOverview`. *Test: log a session as A; as B, history is empty and A's `/history/<id>` is a 404.*
5. **AI routes.** Convert `getCoachingContext`, `getSummaryContext`, `saveTrainingSummary`, `saveCoachingNote`, `getSessionUpdatedAt`; add the `ai_usage` cap. *Test: B's summary mentions only B's training; the 21st call in a day returns 429.*
6. **Starter exercises.** Move the list from `scripts/seed.mjs` into `lib/starterExercises.ts`, insert it in an after-sign-up hook, make the seed script per-user. *Test: a new account has the starter list.*
7. **Client clean-up.** Namespace draft keys by user id, clear on sign-out, show the signed-in email and a change-password form in `app/settings/SettingsForm.tsx`, turn on auth rate limiting.
8. **Isolation test script.** `scripts/test-isolation.mjs`: creates two users, then has B hit every route in section 4 with A's ids and asserts 404 or empty. Run it before every future merge that touches `lib/db.ts`.
9. **Cutover.** Set env vars in Vercel, reset the preview database, test on your phone, reset production, merge, sign up, send friends the invite code. Update `README.md` (it still says "for one person" and documents `APP_PASSWORD`).

## 7. iOS app with lock-screen Live Activities (after accounts)

You asked for an iOS app whose rest timer and session timer show on the lock screen, by whatever route gets there. Accounts ship first (steps 1 to 9), then this.

**Approach: a Capacitor shell around the existing site, plus a small native Swift Live Activity.**

- Live Activities can only be drawn by native SwiftUI code in a Widget Extension. No web or JavaScript-only route exists, so some Swift is unavoidable.
- Capacitor gives a real iOS app whose screen is your existing site, loaded from the Vercel URL. All current UI is reused, and deploys to Vercel update the app without a new build.
- The only native code is the Live Activity layout (roughly 150 lines of SwiftUI) and a small bridge plugin with three calls: start, update, end.
- Sign-in needs nothing extra: the web view keeps the Better Auth cookie like Safari does. The Expo plugin mentioned earlier is not needed.
- Alternative: a full SwiftUI or Expo app. Same Live Activity code, but every screen (including the 837-line session form) is rebuilt and new GET endpoints are needed. Worth it only if you later want the app to feel fully native or work offline.

**How the timers work on the lock screen**

- The Live Activity is given an end time (rest) or a start time (session) and iOS draws the ticking clock itself. The app does not need to be running or send updates, which matters because a web view is paused when the phone locks.
- Rest timer: started from `lib/hooks/useRestTimer.ts` when reps are entered, ended when the rest finishes or is skipped. A local notification scheduled for the end time gives the sound and buzz that the web version cannot produce on a locked phone.
- Session timer: started from `app/components/StartSession.tsx`, ended on save or discard in `SessionForm.tsx`.
- One new file, `lib/native.ts`, detects the Capacitor shell and makes these calls; in a normal browser it does nothing, so the website keeps working unchanged.

**Costs and prerequisites (these break the free-tier goal)**

- Xcode must be installed and selected. This Mac currently has only the command line tools. It is a free but large download from the Mac App Store, followed by `sudo xcode-select -s /Applications/Xcode.app`, which needs your password so you run it yourself.
- Apple Developer Program, $99 a year. **Decided: you will pay for this and aim for the App Store.** Enrol before step 11 so signing is set up once; approval can take a day or two.
- TestFlight comes first as the stepping stone: friends install Apple's TestFlight app and tap a link, and builds last 90 days. An App Store release then removes the expiry and installs like any other app. Website changes reach the app immediately either way.
- **Main risk: Apple can reject apps that are mostly a wrapped website (guideline 4.2).** The Live Activity, end-of-rest notifications and haptics are what make this more than a wrapper, so they must be finished and visible to the reviewer before submitting. If it is still rejected, friends stay on TestFlight and nothing is lost.
- **What App Store review needs that the plan did not have before:** a demo account for the reviewer (sign-up stays invite-only), in-app account deletion, a privacy policy page, the App Privacy form declaring email and workout data, and a clear notice with consent before workout data is first sent to the AI provider. Check the current wording of Apple's rule on third-party AI before submitting.
- If the app is only ever for you and friends, ask Apple for **unlisted distribution**: a normal App Store app with no expiry, reachable only by direct link. Opening sign-up to the public is a separate later decision; it would need email verification and tighter AI limits.
- iPhone on iOS 16.1 or later (Dynamic Island needs 14 Pro or newer; the lock screen works on all).

**Steps**

10. **Install Xcode** and select it (you). *Test: `xcodebuild -version` prints a version.*
11. **Capacitor shell.** Add `@capacitor/core`, `@capacitor/ios`, `@capacitor/cli`, a `capacitor.config.ts` whose `server.url` is the production URL (localhost for dev), generate `ios/`, add app icon and splash. *Test: app runs in the simulator, sign in, log a session.*
12. **Bridge plugin.** Local Swift plugin with `start`, `update`, `end`, plus `lib/native.ts`. *Test: calls from the web console reach Swift logs.*
13. **Live Activity extension.** Widget Extension target, `ActivityAttributes` for rest and session timers, lock-screen and Dynamic Island layouts, `NSSupportsLiveActivities` in `Info.plist`. *Test: start a session in the simulator, lock it, see the clock ticking.*
14. **Wire the timers.** Hook `useRestTimer`, `StartSession` and `SessionForm` to the bridge; schedule the end-of-rest notification. *Test: on a real phone, enter reps, lock, watch the countdown, hear the alert.*
15. **Delete-account endpoint** and a button in Settings. Apple requires it for apps with sign-up; the `ON DELETE CASCADE` keys make it one `DELETE`.
16. **TestFlight.** Create the app record in App Store Connect, archive and upload from Xcode, submit the first build for beta review, send friends the public link. *Test: a friend installs from the link and sees the lock-screen timer.*
17. **App Store readiness.** Add a `/privacy` page, an AI consent notice before the first coaching or summary request, haptics on set completion, and a reviewer demo account created with the seed script. *Test: a fresh account sees the consent notice once; deleting the account removes all its rows.*
18. **Submit.** Screenshots, description, App Privacy form, review notes explaining the invite code and the demo login, then submit (public or unlisted). Expect at least one round of questions from review.
